# etp_assessment_pro — Locust load & concurrency harness

> **Additive-only operator tooling.** Nothing here is auto-discovered by Odoo's
> test runner: this directory is not imported by `tests/__init__.py` and no file
> is prefixed with `test_`. These are scripts you run by hand, not
> `TransactionCase`s.

This harness reproduces the **real candidate journey** through the Odoo website
portal (`controllers/portal.py`, `controllers/candidate_portal.py`) at 200-300+
concurrent candidates. It backs the CONCURRENCY & LOAD items in the feature
matrix and the concurrency-critical open questions in
`docs/ETP_ASSESSMENT_FLOW.md` (open-questions ~line 3702, notably
**#19 no row lock on `_record_response`**, #18 no `access_token` uniqueness,
#24 candidate isolation, #27 synchronous bulk invites).

| File | Purpose |
|---|---|
| `locustfile.py` | The Locust user model + spike `LoadTestShape`. Drives login -> hub -> open day -> begin -> per-question fetch+submit -> review -> finish. |
| `seed_load_data.py` | Idempotent seeder run inside `odoo-bin shell`: builds one single-sitting assessment (category-backed question pool), N portal candidates with a known password, launches the exam so each candidate gets one `evaluator` access token (i.e. N tokens / CSV rows), and writes `candidates.csv`. |
| `candidates.csv` | Generated by the seeder. One row per virtual candidate. Git-ignore in practice. |

## Install

```bash
pip install locust        # optional tooling dep; NOT in the module manifest
```

Locust does not need to be installed to `py_compile` the file, but you need it
to actually run a load test.

## Why the portal path needs no Vertex/LLM budget

`controllers/portal.py::_record_response` (portal.py:572) **never scores
inline**. Subjective answers call `existing._enqueue_subjective_scoring()` and
are graded later by the `_cron_llm_auto_score` cron via `services/scoring.py`
-> `services/vertex.py:_call_vertex`. So the entire concurrent-candidate submit
path exercises only **Postgres + Odoo HTTP workers** — no LLM calls, no model
budget. Keep `llm_auto_score` off (the seeder sets it `False`) or disable the
cron during a run so scoring load does not confound your portal numbers.
**Scoring throughput is a separate test** (drive the cron with
`patch.object(services.vertex, "_call_vertex", ...)`).

## Auth reality (confirmed against source)

The tokenized routes are `auth="public"` but portal.py:79 / portal.py:239
redirect to `/web/login` when `request.env.user._is_public()`. A virtual
candidate MUST first authenticate a portal session (`POST /web/login`, carry the
`session_id` cookie) — the token only scopes *which* day-session. CSRF is
disabled on the POST exam routes (`csrf=False`), so no CSRF token is needed on
begin/submit/finish/violation. The **login form** does need a `csrf_token`,
which the harness scrapes from `GET /web/login`.

## Submit form fields (portal.py:572 `_record_response`)

- `question_id` : int (required)
- `nav` : `"next"` | `"prev"` (drives save-and-advance; portal.py:337)
- `dimension_<QUESTION_DIMENSION_ID>` : per-question option id, or comma-separated
  ids for MSQ (REQUIRED for `mcq` / `msq` / `image_ab`). The field key is
  `dimension_<qd.id>` (the `etp.assessment.pro.question.dimension` id). Values are
  `qd.option_line_ids.ids`; anything not in that set is dropped (portal.py:601).
- `justification` : str (REQUIRED for `subjective_rubric` /
  `image_prompt` / `image_label`; portal.py:585).

## Generating `candidates.csv`

The seeder runs **inside an Odoo shell** (it needs an `env` cursor). Per project
memory, use a THROWAWAY DB (`etp_test_db`), not `ethara`:

```bash
ETP_LOAD_CANDIDATES=300 \
odoo-bin shell -d etp_test_db --no-http \
    < custom_addons/etp_assessment_pro/tests/load/seed_load_data.py
```

> **Seeding suppresses invite emails (important).** `action_generate_plan()`
> normally calls `_send_day_invitation()` on every freshly minted session, which
> runs `tpl.send_mail(rec.id, force_send=True)` (`models/assessment_day.py:335`).
> Every seeded candidate has a valid `email_from`
> (`loadcand_XXXX@loadtest.example.com`), so at 300 candidates × `NUM_DAYS` days
> that is 300·`NUM_DAYS` **blocking** SMTP deliveries **inside the seed
> transaction** — on a throwaway `etp_test_db` with no reachable mail server it
> hangs on connection timeouts or raises `MailDeliveryException` and rolls back
> the entire seed. The seeder therefore neutralizes `mail.template.send_mail`
> for the duration of the launch (`_generate_plan_without_invites`); no invites
> are delivered and none are needed (the harness logs in with the known password
> and drives the token directly). Note that setting `ir.mail_server` to a dead
> host is **not** sufficient — the explicit `force_send=True` still tries to
> connect, so the send must be suppressed, not merely misrouted.

### CSV schema (the harness reads either form)

**PRIMARY (multi-question):**

```
login,password,token,question_plan
```

`question_plan` is URL-safe base64 of a JSON list, in `question_order`, one dict
per question:

```json
[{"qid": 42, "type": "mcq", "dims": {"7": [15]}, "text": ""},
 {"qid": 43, "type": "msq", "dims": {"7": [15, 16]}, "text": ""},
 {"qid": 44, "type": "subjective_rubric", "dims": {}, "text": "My answer"}]
```

- `dims` maps the `dimension_<id>` field to option id(s): single id for
  `mcq`/`image_ab`, a list joined with commas for `msq`.
- `text` is required for `subjective_*` and `image_text`.

The current `seed_load_data.py` emits this PRIMARY (multi-question)
`question_plan` form directly.

**LEGACY (single-question)** — accepted for backward compatibility and
normalized into a one-item plan:

```
email(or login),password,token,question_id,option_id,dimension_field
```

> If you extend the seeder to multi-question days, emit `login,password,
> token,question_plan` and keep the base64 JSON contract above. The harness
> prefers `question_plan` when present and falls back to the legacy columns.

Point the harness at a non-default CSV with `LOCUST_CANDIDATES_CSV=/path.csv`
(the older `ETP_LOAD_CSV` name is still honored).

## Run — steady state (recommended baseline)

```bash
locust -f custom_addons/etp_assessment_pro/tests/load/locustfile.py \
    --headless -u 300 -r 20 -H http://localhost:8069 \
    --run-time 20m --csv run_steady
```

`-u` target users, `-r` spawn rate/sec. When you pass `-u/-r`, Locust controls
the ramp and the `LoadTestShape` stays inactive.

## Run — spike (deadline stampede)

Everyone races the deadline: near-zero think-time, submit/finish pile up at
once. This is the scenario most likely to trip the no-row-lock upsert race
(inventory open-question #19). Two ways:

```bash
# (a) Operator-driven ramp with the spike behavior (no think-time):
LOCUST_SCENARIO=spike locust -f .../locustfile.py \
    --headless -u 300 -r 300 -H http://localhost:8069 --run-time 5m --csv run_spike

# (b) Self-contained shape (warm ramp -> plateau -> 2x spike -> drain). Start
#     WITHOUT -u/-r so the DeadlineSpikeShape drives the profile:
LOCUST_SCENARIO=spike LOCUST_USERS=300 LOCUST_SPAWN_RATE=20 \
    locust -f .../locustfile.py --headless -H http://localhost:8069 --csv run_spike
```

To provoke the same-question double-submit race deliberately, seed **duplicate
rows for the same `token`** (more users than distinct tokens); the harness
wraps around and multiple users then hammer the same evaluator row.

## Run — soak (leaks, connection exhaustion, cron interference)

```bash
locust -f .../locustfile.py --headless -u 250 -r 10 \
    -H http://localhost:8069 --run-time 3h --csv run_soak
```

## Proctoring violations (optional)

Violation POSTs (portal.py:386) are a zero-weight `@task` tagged `violation`,
fired inline from the answer loop when `LOCUST_VIOLATION_PROB` is set:

```bash
LOCUST_VIOLATION_PROB=0.1 locust -f .../locustfile.py --headless -u 300 -r 20 -H ...
# Exclude them entirely:
locust -f .../locustfile.py --exclude-tags violation --headless -u 300 -r 20 -H ...
```

## What to watch (SLAs + server tuning)

**Per-endpoint p95 / error rate.** Requests are named so the Locust stats table
breaks out each endpoint (`POST /pro_assessment/[token]/submit`, `.../finish`,
`GET .../?q=`, `POST /web/login`). Suggested SLA gates for a pass:
- `submit` / `finish` **p95 < 1.5 s**, `GET` question page **p95 < 1 s**.
- **error rate < 0.5%** on any endpoint. A spike of 4xx bouncing to `/web/login`
  means session cookies are being dropped under load (worker/session store).

**Odoo workers.** `--workers N` (gevent/prefork). Concurrent candidates need
enough workers × threads to cover in-flight requests; watch for `--limit-time-
real`/`--limit-time-cpu` worker kills (502/504 to the client) during the spike.
Bump `limit_request` / `limit_memory_*` if workers recycle mid-run.

**DB connections.** Each Odoo worker opens Postgres connections capped by
`db_maxconn`. Total demand ≈ workers × db_maxconn must stay under Postgres
`max_connections` (leave headroom for cron + admin). Connection exhaustion shows
as `OperationalError: FATAL: sorry, too many clients` → 500s. This is the first
thing to blow at 300 users on default configs.

**The no-lock upsert race (inventory open-question #19).** After a spike run,
query for duplicate response rows:
`SELECT assessment_evaluator_id, question_id, count(*) FROM etp_assessment_pro_response
GROUP BY 1,2 HAVING count(*) > 1;` — any group > 1 confirms the missing row
lock / unique constraint under concurrent double-submit.

**Cron / scoring is SEPARATE.** The portal path makes **no Vertex calls**;
keep `_cron_llm_auto_score` disabled during portal load so it does not compete
for workers/DB. Test scoring throughput on its own with the `_call_vertex` mock.

`docs/ETP_ASSESSMENT_FLOW.md` (open questions ~line 3702; test matrix
~line 3281; explicit test gaps at H.7 ~line 3256).
